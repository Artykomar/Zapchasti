# Zemazap: база данных и защита

Дата фиксации: 2026-08-01.

## Решение по базе данных

Для production-версии целевая база данных: PostgreSQL.

Причины:

- каталог запчастей быстро становится реляционным: марки, модели, поколения, категории, OEM-номера, аналоги, поставщики, цены, применимость и заявки;
- нужны индексы, транзакции, импорт прайсов, админка и надежные бэкапы;
- PostgreSQL проще масштабировать до полнотекстового поиска, очередей импорта, отчетов и интеграций.

Для текущей локальной разработки используется SQLite через встроенный модуль Node.js `node:sqlite`.

Причины:

- Docker Desktop пока не установлен, поэтому локальный PostgreSQL сейчас добавил бы лишнюю зависимость;
- SQLite дает настоящие таблицы, индексы, транзакции и файл базы без отдельного сервера;
- схема сделана близко к PostgreSQL-модели, чтобы позже перенести ее в managed PostgreSQL без переписывания интерфейса.

## Текущий контур данных

Файл локальной базы: `data/zemazap.sqlite`.

Источник стартовых seed-данных: текущий демонстрационный каталог в `src/data/catalog.ts`.

Главные таблицы:

- `brands`, `car_models`, `model_generations`;
- `categories`;
- `manufacturers`, `suppliers`;
- `parts`, `part_numbers`, `part_compatibility`, `part_specs`;
- `price_offers`;
- `customer_requests`, `customer_request_items`.

API:

- `GET /api/catalog` - каталог, поиск и фильтры;
- `GET /api/catalog/[slug]` - одна карточка товара;
- `POST /api/requests` - сохранение заявки из формы или корзины.

## Архитектура защиты MVP

Минимальный production-контур:

`домен -> DNS -> WAF/Anti-DDoS -> Next.js frontend/backend -> закрытая PostgreSQL-сеть -> object storage для фото -> бэкапы -> мониторинг`

Базовые правила:

- база данных не открыта в интернет напрямую;
- все секреты только в переменных окружения, не в git;
- HTTPS включен везде;
- формы заявок валидируются на сервере;
- на публичные формы ставится rate limit, позже капча или Turnstile;
- админка только с авторизацией, ролями и 2FA;
- действия администратора пишутся в audit log;
- платежные данные карт не хранятся в нашей базе;
- production и development окружения разделены;
- бэкапы базы и изображений проверяются восстановлением.

## Следующий перенос на PostgreSQL

Когда будет готов сервер или managed PostgreSQL:

1. Завести `DATABASE_URL` в production-окружении.
2. Перенести схему SQLite в миграции PostgreSQL.
3. Заменить `node:sqlite`-репозиторий на PostgreSQL-драйвер или ORM.
4. Оставить API-контракты прежними, чтобы frontend почти не менять.
5. Добавить импорт CSV/XLSX прайсов и админку управления товарами.
