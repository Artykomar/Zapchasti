# Zemazap: внутренняя инструкция по коду перед внешними подключениями

Дата: 2026-08-14.

Назначение: короткий рабочий порядок для команды разработки. Полный исследовательский отчет лежит в [docs/russian-launch-compliance-and-infrastructure-report.md](docs/russian-launch-compliance-and-infrastructure-report.md), а полный TODO внесен в [PROJECT_PLAN_LOG.md](../PROJECT_PLAN_LOG.md) в раздел `TO DO: код перед внешними подключениями`.

## Принцип запуска

До внешних подключений мы должны подготовить код так, чтобы потом оставалось в основном:

- вставить реальные реквизиты ИП/ООО;
- вставить домен и контакты;
- положить секреты банка, кассы, MAX, SMTP и Yandex Cloud в безопасное хранилище;
- переключить `test` на `prod`;
- пройти банковскую и юридическую проверку сайта;
- задеплоить в Yandex Cloud.

Реальные оплаты не включаем, пока у клиента нет выбранного продавца, реквизитов, кассы/ОФД, юридических текстов, решения по ПДн и согласованного сайта.

## 1. Сначала сделать фундамент настроек

1. Вынести контакты, реквизиты и юридические данные в единый конфиг или модель настроек.
2. Добавить production guard: если включены платежи, но нет обязательных реквизитов/секретов/домена, приложение должно явно падать или отключать платежи.
3. Расширить `.env.example` и `backend/.env.example`.
4. Ввести feature flags:
   - `PAYMENTS_ENABLED`
   - `PAYMENTS_MODE=test|prod`
   - `PAYMENTS_PROVIDER=alfa`
   - `FISCALIZATION_ENABLED`
   - `PII_IN_NOTIFICATIONS_ALLOWED=false`
   - `MAX_ENABLED`
   - `ANALYTICS_ENABLED`
5. Сразу договориться, что секреты не попадают в git и не печатаются в логах.

## 2. Потом довести юридические страницы и контакты

Сделать до банковской проверки:

- страница контактов без заглушек;
- `tel:` и `mailto:`;
- MAX-ссылка из конфига;
- реквизиты в футере, контактах и "О компании";
- оферта/условия заказа;
- доставка, оплата, гарантия, возврат;
- политика обработки персональных данных;
- отдельное согласие на обработку персональных данных;
- режим банковской проверки: все обязательные страницы доступны публично и не спрятаны в PDF.

Пока реальные данные не получены, оставляем безопасные заглушки, но production guard не должен позволять включить платежи с заглушками.

## 3. Персональные данные

Нужно сделать до production-форм:

- хранить `consent_version`, `consent_accepted_at`, `consent_source`, IP и user-agent;
- разделить согласие на обработку заявки и согласие на маркетинг;
- добавить версионирование юридических текстов;
- маскировать телефон/email/свободный текст в логах;
- отключить отправку ПДн в Telegram по умолчанию;
- добавить административный поиск/экспорт/удаление или анонимизацию данных субъекта;
- добавить retention policy и management command для очистки/анонимизации старых данных;
- гарантировать, что demo seed не содержит реальных ПДн.

## 4. Разделить заявку и заказ

Текущая `CustomerRequest` - это сырой лид. Платежи нужно привязывать к подтвержденному заказу.

Добавить:

- `Order`;
- `OrderItem`;
- `OrderStatusHistory`;
- `OrderComment`;
- связь `CustomerRequest -> Order`;
- админское действие "Создать заказ из заявки";
- публичную страницу заказа по безопасному токену;
- защиту от повторной оплаты;
- фиксацию финальной суммы, доставки, НДС/без НДС и состава заказа.

Минимальный рабочий сценарий:

1. Покупатель оставляет заявку.
2. Менеджер проверяет применимость, срок, цену и доставку.
3. Менеджер создает подтвержденный заказ.
4. Покупатель получает ссылку на страницу заказа.
5. Только там появляется кнопка оплаты, если `PAYMENTS_ENABLED=true`.

## 5. Платежи Альфа-Банка

Сделать отдельный модуль `payments`.

Минимальные модели:

- `Payment`;
- `PaymentEvent`;
- `PaymentAttempt`;
- `Refund`, если возвраты делаем в том же модуле.

Минимальные функции:

- API-клиент Альфа-Банка с test/prod URL из env;
- создание платежной ссылки только для подтвержденного заказа;
- сохранение `bank_order_id`, `form_url`, суммы, валюты и статуса;
- страницы `success` и `fail`;
- callback endpoint;
- server-to-server проверка статуса после callback;
- ручная проверка статуса в админке;
- периодическая сверка зависших платежей;
- mock-клиент банка для тестов.

Правила безопасности:

- не принимать данные карты на нашем сайте;
- не хранить PAN/CVV/срок действия;
- не доверять redirect из браузера как факту оплаты;
- проверять сумму и номер заказа;
- обрабатывать повторные callback идемпотентно;
- логировать платежные события без секретов и карточных данных.

## 6. Фискализация, касса и ОФД

Даже если реальный провайдер кассы будет выбран позже, код должен быть готов.

Добавить:

- `FiscalReceipt`;
- `FiscalReceiptItem`;
- `FiscalReceiptEvent`;
- абстракцию `FiscalProvider`;
- тестовый provider, который валидирует чек без отправки наружу;
- поля товара для чека: название, НДС/без НДС, признак предмета расчета, признак способа расчета, единица;
- чек прихода после успешной оплаты;
- чек возврата при возврате платежа;
- админский критический статус "оплата есть, чек не пробит";
- retry и ручную проверку.

## 7. Возвраты и претензии

Добавить:

- `Refund`;
- `RefundItem`;
- `Claim`;
- полный и частичный возврат;
- запрет возврата больше оплаченной суммы;
- связь возврата с платежом, заказом и фискальным чеком;
- журнал действий менеджера;
- уведомление клиента;
- фиксацию состояния и комплектности контрактных/восстановленных деталей.

## 8. Товары, маркировка и документы

Добавить в товарную модель/админку:

- состояние: новый, контрактный, восстановленный, б/у;
- реальное или иллюстративное фото;
- гарантийные условия;
- документы соответствия;
- потенциальная маркировка;
- warning для категорий вроде шин, масел, фильтров, стекол, свечей и других потенциально маркируемых групп;
- импорт этих полей из CSV/XLSX.

Если категория требует маркировку, в админке должно быть видно, что продавать ее нельзя без готового процесса учета.

## 9. Yandex Cloud readiness

До реального деплоя подготовить:

- Dockerfile/Docker Compose или другой production build;
- production/staging/dev настройки;
- health endpoints;
- подключение к PostgreSQL через `DATABASE_URL`;
- миграции на пустой production-like базе;
- Object Storage для фото и документов;
- secrets contract под Yandex Lockbox;
- структурированные логи без ПДн и секретов;
- backup/restore runbook;
- smoke-check после деплоя;
- rollback-инструкцию.

Целевая схема:

```text
Домен -> DNS -> TLS/ALB -> WAF -> Next.js + Django -> Managed PostgreSQL
                                   -> Object Storage
                                   -> Lockbox
                                   -> Monitoring/Logging
```

## 10. Админка и доступы

Перед production:

- убрать временный общий пароль;
- использовать нормальных пользователей Django;
- добавить роли;
- добавить 2FA;
- добавить audit log;
- добавить rate limit login;
- рассмотреть IP allowlist или дополнительную защиту `/admin`;
- не показывать секреты в админке;
- разделить права на заявки, ПДн, платежи, возвраты, реквизиты и импорт.

## 11. Уведомления

Сделать единый notification service:

- email;
- admin/web notifications;
- MAX позже;
- Telegram только в безопасном режиме.

Шаблоны:

- новая заявка;
- подтвержденный заказ;
- ссылка на оплату;
- успешная оплата;
- ошибка оплаты;
- возврат;
- ошибка фискализации.

Сбой уведомления не должен ломать создание заявки или оплату. Нужны retries и журнал доставок.

## 12. Тестовый сценарий готовности

Перед внешними подключениями должен проходить end-to-end в test/mock:

1. Создать заявку из формы.
2. Создать заказ из заявки в админке.
3. Сгенерировать тестовую платежную ссылку.
4. Получить успешный callback mock-банка.
5. Проверить server-to-server статус mock-банка.
6. Перевести заказ в `paid`.
7. Создать тестовый фискальный чек.
8. Отправить безопасное уведомление менеджеру.
9. Сделать частичный или полный возврат.
10. Создать тестовый чек возврата.

Обязательные проверки:

- `manage.py check`;
- Django tests для catalog/leads/imports/notifications/orders/payments/fiscalization;
- `npm.cmd run typecheck`;
- `npm.cmd run build`;
- сценарий отказа оплаты;
- дубль callback;
- неверная сумма;
- отсутствие утечки карточных данных;
- отсутствие отправки ПДн в Telegram без разрешения;
- production guard с отсутствующими реквизитами.
