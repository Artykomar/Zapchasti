# Альфа-Банк и фискализация: порядок включения

Дата актуализации: 2026-08-20.

## 1. Что уже реализовано в коде

- регистрация одностадийного заказа через `register.do`;
- оплата только на защищенной странице банка: Zemazap не принимает реквизиты карты;
- server-to-server проверка через `getOrderStatusExtended.do`;
- строгая сверка `orderNumber`, суммы в копейках, валюты и списанной суммы;
- callback не доверяет присланному статусу и всегда запускает server-to-server проверку;
- ручная проверка статуса из Django Admin и команда `reconcile_pending_payments`;
- полный и частичный возврат через `refund.do`, лимит суммы и идемпотентность;
- передача товарной корзины `orderBundle` для фискализации через подключенный к Альфа-Банку ОФД;
- mock-режим для локальных тестов, который невозможно включить вместе с production-платежами.

## 2. Данные, которые должен получить владелец бизнеса

1. Подать заявку на интернет-эквайринг и получить тестовые, затем production-реквизиты.
2. Создать пароль API-пользователя с суффиксом `-api` либо получить API token.
3. Согласовать одностадийную схему, валюту RUB и возможность полных/частичных возвратов.
4. Выбрать партнера онлайн-кассы/ОФД: АТОЛ, Orange Data, OFD.ru либо другой согласованный сервис.
5. Настроить фискализацию и систему налогообложения в кабинете Альфа-Банка.
6. Передать инженеру только ссылки/идентификаторы секретов. Сами секреты поместить в Yandex Lockbox.

Официальный процесс подключения: <https://alfabank.ru/sme/payservice/internet-acquiring/docs/process/>.

## 3. Переменные окружения

Обязательные для production:

```text
PAYMENTS_ENABLED=true
PAYMENTS_PROVIDER=alfa
PAYMENTS_MODE=prod
ALFA_BANK_GATEWAY_URL=https://pay.alfabank.ru/payment/rest
ALFA_BANK_USERNAME=<логин-api>
ALFA_BANK_PASSWORD=<секрет>
# Вместо пары логин/пароль может использоваться ALFA_BANK_TOKEN.
ALFA_BANK_CALLBACK_TOKEN=<случайный длинный секрет>
FISCALIZATION_ENABLED=true
FISCAL_PROVIDER=alfa
FISCAL_TAX_SYSTEM=<код 0-5 по договору и настройкам кассы>
```

Тестовый gateway задается значением, выданным банком; в актуальной документации банка используется среда `alfa.rbsuat.com`. Не переносить тестовые логины в production.

Callback URL регистрируется с секретом в query string:

```text
https://<домен>/api/payments/alfa/callback/?token=<ALFA_BANK_CALLBACK_TOKEN>
```

Секрет не добавлять в GitHub, `.env.example`, логи или URL репозитория.

## 4. Обязательная приемка до реальных денег

1. Заполнить реальные реквизиты, контакты, адрес, условия доставки/возврата и юридические тексты.
2. Выполнить `python backend/manage.py check --deploy` без ошибок Zemazap.
3. Провести успешный и неуспешный тестовый платеж по тестовым картам банка.
4. Проверить повтор callback, неверную сумму, неизвестный заказ и повторную оплату.
5. Провести частичный и полный тестовый возврат.
6. Убедиться в личном кабинете кассы/ОФД, что чек прихода и чек возврата сформированы с правильным НДС и номенклатурой.
7. Только после одобрения банка, бухгалтера и владельца заменить test-реквизиты на production и включить флаги.

## 5. Эксплуатация

- Планировщик запускает `reconcile_pending_payments` каждые 5 минут.
- Планировщик запускает `retry_failed_receipts` и `retry_notifications` каждую минуту.
- Состояние «оплата прошла, чек не пробит» является критическим и требует немедленной проверки.
- При сбое банка не менять статус вручную на `paid`; сначала выполнить server-to-server сверку.
- Возврат создается и проводится только пользователем с правом `process_refund`.
- Возврат, оставшийся в `processing` после сетевого сбоя/рестарта, нельзя запускать повторно вслепую: сначала сверить возвращенную сумму через банк, чтобы исключить двойной возврат.
