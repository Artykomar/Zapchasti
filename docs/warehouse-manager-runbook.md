# Кабинет склада Zemazap

Дата: 2026-08-28. Реализован в существующем Django backend; витрина Next.js,
платежи и production-маршрут через Yandex/Caddy сохранены.

## Вход

Локальный адрес: `http://127.0.0.1:8000/admin/warehouse/`.
В основной админке появилась ссылка **Открыть рабочий стол склада**.
Переход через Next.js `/admin/warehouse/` сохраняет путь и фильтры.
В production маршрут уже обслуживается существующим правилом Caddy `/admin*`.

После обновления кода:

```powershell
.\.venv\Scripts\python.exe backend\manage.py migrate
.\.venv\Scripts\python.exe backend\manage.py bootstrap_roles
.\.venv\Scripts\python.exe backend\manage.py collectstatic --noinput
```

Перезапустите Django в PyCharm. Владелец назначает сотруднику группу
`warehouse_manager`, флаги **Активный** и **Статус персонала**. Пароль задаётся
обычным способом в Django; новый общий пароль или обход входа не создаются.
Superuser и группа `owner` имеют доступ. Само создание группы не назначает её
существующим сотрудникам.

Роль склада может работать с деталями, поставщиками, закупками, резервами и
отправлениями. Она видит необходимое для доставки ФИО/контакт, но не получает
прав на пользователей, настройки магазина, создание платежей или возврат денег.
Подтверждение клиентской заявки и выставление ссылки на оплату остаются у
менеджера в основной админке.

## Рабочий процесс

1. **Детали и остатки.** Найдите артикул/OEM или создайте деталь. Заполните ячейку,
   минимальный остаток и реальный вес одной детали в граммах. Основное ценовое
   предложение обновляет витрину, не цену в уже созданном заказе.
2. **Начальный учёт.** Проведите инвентаризацию. Запишите корректировку с причиной:
   `+5` означает добавить пять единиц, `−2` — списать две. Текст «100 у поставщика»
   не переносится в физический остаток. «Не считали» не означает наличие товара.
3. **Закупки.** Выберите поставщика, срок, детали, количество и закупочную цену.
   Можно добавить до 50 строк. Создание черновика и отметка о согласовании поставки
   не отправляют заказ поставщику и не оплачивают счёт.
4. **Приёмка.** Переведите закупку в ожидание поставки. Принимайте фактически
   проверенные количества по строкам. Поддерживается частичная приёмка; превышение
   заказанного количества запрещено. Повтор отправки той же формы не повторяет
   приход. Частично принятую закупку нельзя отменить одним действием.
5. **Заказы покупателей.** Подтверждённый или оплаченный заказ можно взять в
   сборку, если все позиции привязаны к каталогу и хватает свободного остатка.
   Резерв проверяется по всем позициям одной транзакцией. Лист сборки можно печатать.
6. **Упаковка.** Доступна только после подтверждённой оплаты. Если состав заказа
   изменён после резервирования, нужно снять резерв и собрать заказ заново.
7. **СДЭК.** Откройте заказ, сохраните получателя, город, ПВЗ/адрес, вес с упаковкой
   и размеры. Сначала сохраняется локальный черновик. Расчёт тарифа, регистрация
   и запрос печатной формы — отдельные действия.
8. **Отгрузка.** После физической передачи посылки подтвердите её в карточке заказа.
   Нужны статус «Упакован», оплата и зарегистрированная production-накладная.
   Только это действие уменьшает физический остаток и резерв. Тестовая накладная
   списание не разрешает. Финансовый статус заказа не изменяется.

Все изменения остатков сохраняют автора, время, изменение количества/резерва,
остаток после операции и связанный заказ/закупку. Складские модели в стандартной
админке доступны только для чтения, чтобы не обходить сервисы учёта.

## Подключение СДЭК

По умолчанию `CDEK_ENABLED=false`, `CDEK_MODE=test`. Без подключения можно вести
склад, приёмки, резервы и сохранять черновики доставки. Сетевых вызовов СДЭК нет.

Заполняйте только `backend/.env` локально или секреты backend в инфраструктуре:

```dotenv
CDEK_ENABLED=false
CDEK_MODE=test
CDEK_CLIENT_ID=
CDEK_CLIENT_SECRET=
CDEK_TIMEOUT_SECONDS=15
CDEK_SENDER_NAME=
CDEK_SENDER_PHONE=
CDEK_SENDER_CITY_CODE=0
CDEK_SENDER_ADDRESS=
```

Ключи не должны попадать в Git, чат, frontend или `NEXT_PUBLIC_*`. Тестовый и
рабочий контуры используют разные ключи; сохранённая накладная привязана к своему
контуру. API адреса фиксированы: тест `api.edu.cdek.ru/v2`, рабочий `api.cdek.ru/v2`.
После получения тестовых ключей и заполнения отправителя включите API в тестовом
окружении и перезапустите Django. Не включайте production без приёмки владельцем.

Текущий объём интеграции: одна посылка на заказ, тарифы **136** (склад → ПВЗ) и
**137** (склад → дверь), предоплаченные товары, без наложенного платежа. Город и
код ПВЗ вводятся по справочнику СДЭК; интерактивная карта/поиск ПВЗ не реализованы.
Вес товара в карточке и вес посылки — разные величины; посылка не может весить
меньше суммы деталей. Цена калькулятора — оценка, не окончательный счёт.

Создание отправления требует отдельного подтверждения менеджера. HTTP 202/UUID
не считается завершённой регистрацией: затем нужно получить номер накладной
через **Обновить статус**. Печатная форма также создаётся асинхронно; если PDF ещё
не готов, повторите скачивание позже. PDF отдаётся через защищённый backend,
не по произвольной ссылке из ответа провайдера.

Источник контракта: [официальная документация СДЭК API](https://apidoc.cdek.ru/),
раздел `api_v2_integration`, официальная спецификация
`https://gateway.cdek.ru/api-cdek-docs/web/docs/merged?sectionId=api_v2_integration`,
получена 2026-08-28. Используются `/v2/oauth/token`, `/v2/calculator/tariff`,
`/v2/orders`, `/v2/orders/{uuid}`, `/v2/print/orders` и PDF endpoint.

## Ошибки и сверка

- После тайм-аута отправление остаётся в состоянии **Проверить регистрацию**.
  Повторный POST создания блокируется. Сверка ищет прежнюю заявку по UUID или
  уникальному номеру магазина `im_number`. Если ответ остаётся неоднозначным,
  проверьте этот номер в кабинете СДЭК и обратитесь к ответственному за интеграцию.
  Не создавайте дубликат и не сбрасывайте статус вручную без сверки с перевозчиком.
- Ошибочная/отменённая зарегистрированная накладная в этой версии исправляется
  в кабинете СДЭК; затем обновляется статус в Zemazap. Автоматического повторного
  создания, отмены через API, вызова курьера и разделения на несколько посылок нет.
- Активная или неопределённая накладная блокирует снятие резерва. После подтверждённой
  отмены перевозчиком резерв можно снять. Возврат/невручение не создаёт приход:
  физическое возвращение товара проверяется и записывается отдельно.
- Существующий `run_operations_scheduler` вызывает `sync_cdek_shipments` для
  ограниченной очереди уже отправленных заявок. Он не создаёт накладные и не
  списывает товар. При выключенном API команда ничего не отправляет.

```powershell
.\.venv\Scripts\python.exe backend\manage.py sync_cdek_shipments --limit 25
```

## Приёмка перед рабочим использованием

Локальные тесты проверяют бизнес-правила, CSRF/RBAC, рендер страниц и ответы
адаптера с имитацией СДЭК. Это не подтверждение работы реального договора СДЭК.

До production необходимы: тестирование с выданными ключами, корректность кодов
городов/ПВЗ, тарифа, плательщика доставки по договору, реального PDF, тайм-аута и
сверки, отмены и невручения; проверка конкурентной работы на PostgreSQL; приёмка
интерфейса сотрудником. Согласуйте хранение данных получателей и передачу в СДЭК
с владельцем политики ПДн. Отдельное удаление/анонимизация полей новых отправлений
ещё не включено в существующий retention-процесс и остаётся release-задачей.

Старые задачи CEO по юридическим документам, Yandex Cloud, Альфа-Банку и ККТ/ОФД
не закрываются появлением складского кабинета. Автоматического deployment нет.
